# Chat-First Point.ai Design

**Date:** 2026-04-20  
**Status:** Approved for planning  
**Scope:** Product shell + persistence model + tool invocation model for a minimalist chat-first Point.ai

---

## 1. Problem

Point.ai currently exposes multiple visible workspaces (`Image workspace`, `CAD workspace`) and several persistent controls. That is useful for feature exploration, but it makes the product feel like a technical tool rather than an AI agent.

The desired end state is simpler:

- login
- projects
- threads/chats inside a project
- one primary chat surface

The agent should still be able to:

- generate a floor plan from an image
- analyze and fit a floor plan against a site plan
- later perform deterministic room-level wall adjustments
- export DXF and related artifacts

The simplification must not sacrifice:

- persistence
- version history
- reversibility
- artifact traceability
- geometric validation

---

## 2. Core Decision

Point.ai should become **chat-first, not chat-only**.

That means:

- the **main interface** is a single conversation surface
- the **tool outputs** appear as contextual artifacts inside the chat
- the **source of truth** remains persisted in product data structures, not in downloaded files

Downloads are exports. They are not the canonical state.

---

## 3. Product Model

### 3.1 Project

A project represents the durable business/work unit:

- one client
- one property or lot
- one design effort

### 3.2 Thread

A thread represents one conversational workflow inside a project.

Examples:

- "Generate floor plan from image"
- "Fit Dawson to site plan"
- "Resize option A"

### 3.3 Artifact

An artifact is a versioned result generated by tools during the thread.

Examples:

- parsed floor plan
- CAD extraction result
- site-fit overlay
- adjusted floor plan preview
- exported DXF
- validation report

### 3.4 Version

Each artifact can have versions so the user can:

- compare
- undo
- branch
- export a chosen result

---

## 4. UX Principles

### 4.1 Minimal shell

The default UI should feel as simple as Claude or ChatGPT:

- left: project/thread navigation
- right: one chat

No permanent dense control panels should dominate the screen.

### 4.2 Progressive disclosure

Technical controls appear only when needed:

- upload controls when the task needs files
- preview cards when geometry needs review
- action buttons when the agent proposes an operation
- export buttons only after a valid artifact exists

### 4.3 Agent-led, user-directed

The user tells Point.ai what they want. The agent chooses the right tool path, but the system remains reviewable and deterministic.

Examples:

- "Generate a floor plan from this image"
- "Check whether this house fits in this site plan"
- "Move the east wall of BEDROOM 2 by 18 inches"

### 4.4 Geometry must stay inspectable

Even in a minimal chat UI, geometry-heavy tasks still need explicit visual artifacts:

- overlays
- room highlights
- overflow marking
- measurement cards
- DXF exports

The product can hide complexity, but it must never hide truth.

---

## 5. Architecture

### 5.1 Frontend shell

Replace visible workspace switching with a chat-first shell:

- login page
- project list
- thread list per project
- thread detail page with one chat surface

Within the thread, messages can render:

- text responses
- file attachments
- artifact cards
- inline preview panels
- apply/undo/export actions

### 5.2 Existing backend capabilities remain separate

The backend already has isolated capabilities:

- image parsing / floor-plan generation
- CAD extraction
- site-fit analysis

These should remain as bounded contexts. The chat layer becomes an orchestration surface over them.

### 5.3 Artifact-oriented orchestration

Each tool call should create or update artifacts tied to the thread:

- input files
- normalized geometry
- room extraction
- fit analysis
- adjustment previews
- exports

### 5.4 Deterministic mutation path

Future room-level resizing should not be implemented as free-form AI drawing.

The approved future approach is:

1. user intent captured in chat
2. converted into a structured mutation command
3. deterministic geometry engine applies the change
4. validator checks geometry + constraints
5. new artifact version is created

---

## 6. Decomposition into Subprojects

This overall direction is too large for one implementation plan. It should be split into these subprojects:

### Subproject A — Chat-first shell and persistence

Goal:

- make the product feel like projects + threads + one chat surface
- preserve current persistence guarantees
- keep existing tools callable behind the scenes

### Subproject B — Artifact cards and tool execution model

Goal:

- render image generation, CAD extraction, site-fit analysis, and exports as chat artifacts
- keep contextual apply/download actions inside the thread

### Subproject C — Deterministic room-level wall move workflow

Goal:

- add a structured adjust flow inside the chat for selecting a room/wall and moving it by explicit inches

### Subproject D — Geometry mutation engine

Goal:

- implement shared-wall updates, remeasurement, validation, and DXF regeneration

---

## 7. Recommended First Implementation

The first implementation plan should cover **Subproject A only**.

Why:

- it delivers the product-direction change the user wants
- it reuses current working capabilities
- it reduces UX complexity immediately
- it creates the correct container for later CAD/site-fit/adjustment work

This first slice should:

- keep current project persistence
- reinterpret current plan persistence as thread/artifact persistence
- introduce a minimalist thread screen
- preserve existing tool entry points behind chat actions

It should **not** yet implement the full room-mutation engine.

---

## 8. Data Model Direction

### 8.1 Reuse before rewrite

Current persisted entities already include projects and plans. The first slice should reuse as much of that model as possible rather than doing a risky storage rewrite.

Practical mapping for the first slice:

- existing `ProjectData` remains `Project`
- existing `PlanData` can back an initial `Thread` record
- generated outputs become lightweight artifact records attached to the thread

### 8.2 Canonical state

Canonical state should live in:

- project metadata
- thread transcript
- artifact versions
- structured tool outputs

Canonical state should **not** live only in downloaded DXFs or images.

---

## 9. Error Handling

The chat-first UX still needs explicit failure modes.

If a tool fails:

- the thread gets a failure message
- the failure is attached to the attempted artifact
- the user sees the exact operation that failed
- retry remains local to that artifact/action

If geometry confidence is low:

- the system should say so
- the artifact should be marked unresolved or review-needed

It must not silently bluff.

---

## 10. Testing Strategy

### Frontend

- state transitions between login / projects / thread view
- rendering of artifact cards inside chat
- minimal shell regression tests
- navigation without workspace tabs

### Backend

- existing tool APIs remain backward-compatible
- artifact orchestration endpoints return stable contracts
- persistence mapping from current plan model to thread/artifact model

### End-to-end confidence

At least one realistic flow should work:

1. create/open project
2. open thread
3. upload source
4. run one tool
5. render artifact in chat
6. export downloadable file

---

## 11. Tradeoffs

### Why this is better than keeping separate visible workspaces

Pros:

- simpler product feel
- better AI-agent story
- less cognitive switching
- easier narrative across generation, fit, and adjustment

Cons:

- requires a new orchestration shell
- some advanced controls become one click deeper
- chat rendering must be designed carefully to avoid hiding technical truth

### Why this is better than true chat-only with no artifacts

Pros:

- preserves inspectability
- safer for CAD/geometry workflows
- supports validation and export

Cons:

- slightly more implementation work than a plain text chat UI

---

## 12. Final Recommendation

Point.ai should evolve into a **minimalist chat-first product shell** backed by durable projects, threads, and artifacts.

The first implementation should focus on the shell and persistence model, not on full geometric adjustment yet.

That gives the product the right feel immediately while preserving the engineering foundation needed for deterministic CAD/site-fit workflows later.
